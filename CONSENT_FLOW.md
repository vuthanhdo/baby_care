# BabyCare consent flow

## Runtime contract

After authentication, the iOS app calls `babycare_consent_status` and opens the
Privacy & Consent screen unless the accepted Terms, Privacy, and Health Data
versions all match the current server requirements. The three confirmations are
submitted together through `babycare_accept_consent`; the authenticated user is
always derived from `auth.uid()` and all acceptance times are generated by the
database. The app does not store a local “accepted” flag.

The database reuses `babycare_private.require_current_consent()` at the mutation
RPC/table boundary and on protected Storage writes. Missing or outdated consent
raises `CONSENT_REQUIRED`. Reads and erasure remain available. A blocked cloud
write stays in the device outbox and can resume with the same operation ID after
re-consent.

## Versions and existing users

`public.consent_requirements` is the server source of truth. Documents bundled in
this app release are version `1.0`; deploy new document content in an app release
before changing the corresponding required server version. Existing accounts and
child/health records are not changed. Accounts without a matching audit record
must explicitly consent; timestamps are never fabricated.

Append-only audit records are retained for old versions and are removed with the
auth user by the existing account-erasure flow. Changing a required version adds
a new audit row after acceptance instead of rewriting the prior record.

Rollback should disable the new guards/policies and restore the public
`babycare_apply` implementation, but should not delete `user_consents`: those rows
are audit evidence. A rollback re-enables writes without consent and therefore
requires an explicit product/privacy decision.

## Known operational limits

- Initial consent validation is fail-closed and requires network access, including
  when the user keeps child data only on this device. The account and consent audit
  still live on Supabase; on-device child data is not uploaded automatically.
- SQL tests exercise PostgreSQL functions, RLS, triggers, and Storage policies in
  an isolated PGlite database. Staging must still cover GoTrue JWT handling,
  PostgREST error serialization, and the Supabase Storage HTTP service.
- The app offers account/child deletion, not independent withdrawal toggles for
  each consent category. Do not claim a backup-erasure deadline that the current
  infrastructure has not verified.
